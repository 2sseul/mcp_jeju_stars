# Jeju-Star MCP — 로컬 sLLM 연동 정량 평가 가이드라인

작성일 2026-08-20 · 대상 커밋 `b42ca7b` (deploy) · 하드웨어 RTX 5060 8GB

---

## 0. 이 문서가 정하는 것

"MCP 서버를 붙이니까 좋아졌다"를 **숫자로** 말하기 위한 실험 규약이다.
무엇을 재고(지표), 무엇을 고정하고(통제 변수), 무엇과 비교하는지(베이스라인)를
먼저 못 박는다. 측정 코드(`bench/`)는 이 문서를 그대로 구현한다.

핵심 질문 셋:

1. **되는가** — 로컬 sLLM 이 이 서버의 도구 셋을 **올바르게 고르고 올바른 인자로** 부르는가.
2. **나아지는가** — 같은 모델·같은 질문에서, 도구 없는 답변 대비 **사실 정확도**가 얼마나 오르고 **환각**이 얼마나 줄었는가.
3. **쓸 만한가** — 그 개선을 **몇 초**에 사는가. 그 시간 중 **도구 로직이 먹는 몫**은 얼마인가.

## 1. 시스템 구성 — 컨테이너 3개, 네트워크 1개

Host LLM 과 MCP 서버는 **서로 다른 컨테이너**이고, 같은 도커 브리지 네트워크
`etri-jejuax-gateway-network` 위에서 **컨테이너 이름으로** 통신한다. 호스트
포트 매핑은 사람이 들여다볼 때만 쓰고, 측정 트래픽은 전부 네트워크 내부로 흐른다.

```
                 etri-jejuax-gateway-network (bridge)
   ┌──────────────────────────────────────────────────────────────┐
   │                                                              │
   │  ┌────────────────────┐          ┌────────────────────────┐  │
   │  │ etri-jejuax-ollama │          │ etri-jejuax-jeju-star- │  │
   │  │  ollama/ollama     │          │ mcp                    │  │
   │  │  GPU: --gpus all   │          │  FastMCP streamable    │  │
   │  │  :11434            │          │  HTTP  :11000  (경로 /)│  │
   │  │  = Host LLM 런타임 │          │  = MCP 서버            │  │
   │  └─────────▲──────────┘          └───────────▲────────────┘  │
   │            │ HTTP /api/chat                  │ MCP           │
   │            │                                 │ (streamable   │
   │  ┌─────────┴─────────────────────────────────┴──── HTTP)     │
   │  │ etri-jejuax-bench                                      │  │
   │  │  = Host 애플리케이션 (MCP 클라이언트 + 에이전트 루프)  │  │
   │  │  측정·채점·리포트                                      │  │
   │  └────────────────────────────────────────────────────────┘  │
   └──────────────────────────────────────────────────────────────┘
```

**왜 3개인가.** MCP 의 "Host" 는 *LLM 을 들고 있는 애플리케이션*이다. 여기서
LLM 추론(Ollama)과 에이전트 루프(bench)를 갈라 둔 것은 두 가지 때문이다.

- Ollama 공식 이미지에는 파이썬이 없어 하네스를 같이 넣으려면 이미지를 다시 구워야 한다.
- **시간을 분해하려면 세 지점이 따로 있어야 한다.** 추론 시간은 Ollama 응답이,
  도구 시간은 MCP 왕복이, 나머지 오버헤드는 bench 가 각각 재야 서로 섞이지 않는다.

즉 요구사항인 "Host LLM 컨테이너 ≠ MCP 서버 컨테이너, 같은 네트워크"는 지켜지고,
bench 는 그 둘을 **밖에서 재는 계측기**다.

**측정 대상 주소**(컨테이너 안에서 본 것):

| 대상 | 주소 |
|---|---|
| LLM | `http://etri-jejuax-ollama:11434` |
| MCP | `http://jeju-star-mcp-server:11000/` (streamable HTTP, 경로는 루트) |

> 주의: MCP 서버는 `app.mount("/", mcp_app)` 로 루트에 MCP 를 물려 두었으므로
> `/recommend-spots` 같은 REST 경로는 **밖에서 404 다**. 도구는 오직 MCP 프로토콜로만
> 열린다. 하네스도, 정답 생성도 전부 MCP 클라이언트로 부른다 — 실제 배포 경로와 같게.

## 2. 비교군(arm) 정의

같은 모델·같은 질문·같은 디코딩 설정에서 **도구 접근권만** 바꾼다.

| arm | 이름 | LLM | MCP 도구 | 무엇을 말해 주나 |
|---|---|---|---|---|
| **A** | `baseline` | ○ | ✗ | 모델이 **제 지식만으로** 답할 때의 사실 정확도·환각 (개선의 분모) |
| **B** | `mcp` | ○ | ○ | 도구를 붙였을 때의 정확도·환각·지연 (개선의 분자) |
| **T** | `tool-floor` | ✗ | ○ | LLM 없이 도구만 직접 호출. **정답(ground truth) 생성 + 도구 로직 시간의 하한** |

- A 와 B 는 **시스템 프롬프트의 역할 문장까지 동일**하다. 다른 것은 도구 스키마가
  붙느냐뿐이다. 프롬프트 차이로 생긴 개선을 도구 덕으로 오해하지 않기 위해서다.
- A 에게도 "모르면 모른다고 답하라"를 똑같이 준다. 베이스라인을 일부러 불리하게
  세우지 않는다 — 그래야 개선폭이 과장되지 않는다.
- T 는 arm 이라기보다 **자(尺)** 다. 정답도 여기서 나오고, §5 의 도구 시간 기준선도 여기서 나온다.

## 3. 평가 대상 모델 (6종)

| 모델 | 파라미터 | Q4 VRAM | Ollama 태그(예정) | 비고 |
|---|---|---|---|---|
| Kanana-2-3B-instruct (카카오) | 3B | ~2.0GB | `hf.co/…kanana…:Q4_K_M` | 한국어 특화 |
| A.X 4.0 Light (SKT) | 7B | ~4.4GB | `hf.co/…A.X-4.0-Light…:Q4_K_M` | 한국어 특화 |
| EXAONE-3.5-7.8B-Instruct (LG) | 7.8B | ~4.8GB | `exaone3.5:7.8b` | 한국어 특화 |
| qwen3.5:4b | 4B | ~3.4GB | `qwen3.5:4b` | 도구 호출 강함 |
| gemma4:e2b-it-qat | E2B | ~4.3GB | `gemma4:e2b-it-qat` | QAT |
| llama3.1:8b | 8B | ~4.9GB | `llama3.1:8b` | 도구 호출 레퍼런스 |

**8GB VRAM 이므로 한 번에 한 모델만 적재한다.** 모델 전환 시 이전 모델을 내리고
(`keep_alive: 0`), 다음 모델을 올린 뒤 **워밍업 1회**를 버린다. 모델 적재
시간(cold load)은 어떤 지연 지표에도 포함하지 않는다.

**도구 호출 방식은 모델마다 다를 수 있다.** 두 모드를 두고, 케이스마다 어느 모드로
돌았는지 기록한다.

- `native` — Ollama `/api/chat` 의 `tools` 필드(모델 템플릿이 지원할 때).
- `prompted` — 지원하지 않으면 시스템 프롬프트에 도구 스키마를 JSON 으로 싣고
  `{"tool":…,"arguments":{…}}` 한 줄을 뱉게 한다.

**모드가 다르면 같은 표에서 순위를 매기지 않는다.** 모드는 결과 표에 열로 남기고,
비교는 모드가 같은 모델끼리 한다. 도구를 못 붙이는 모델이 있다는 사실 자체도 결과다.

## 4. 평가 데이터셋

케이스 **24개**. 각 케이스는 사람이 쓰듯 쓴 한국어 질문 하나와, 정답 판정에 필요한
메타데이터를 갖는다.

```python
{
  "id": "R-03",
  "category": "recommend",
  "question": "제주공항에서 40분 안에 갈 수 있는 별 보기 좋은 곳 3군데 알려줘.",
  "gold_tool": "recommend_spots",                      # 기대 도구 (None = 도구 부르면 안 됨)
  "gold_args": {"origin": "제주공항", "max_drive_minutes": 40, "limit": 3},
  "required_args": ["origin", "max_drive_minutes"],    # 이것만 맞으면 정답 취급
  "fact_keys": ["spots[].name", "spots[].drive.minutes"]  # 답변에 실려야 하는 근거
}
```

**구성 (도구 분포를 실제 사용 비율에 맞춘다):**

| 범주 | 개수 | 무엇을 보는가 |
|---|---|---|
| `recommend` | 7 | 지역·주행시간·등산 여부·주차·반려동물·도보 조건이 **인자로 옮겨지는가** |
| `evaluate` | 8 | 지명/좌표 두 입력형, `scope=moment` vs `night` 구분, 미등록 장소, 미래 날짜 |
| `details` | 5 | 접근성 질문을 `evaluate_place` 가 아니라 `spot_details` 로 보내는가 |
| `no-tool` | 4 | **도구를 부르면 안 되는 질문**. 과잉 호출(false positive) 측정 |

**설계 규칙:**

1. **도구 이름을 질문에 흘리지 않는다.** "recommend_spots 써서" 같은 힌트 금지.
   사용자가 실제로 쓸 말("등산 안 하고 차 대고 바로 보는 데")로만 묻는다.
2. **한 케이스는 한 도구.** 다단계(도구 2개 연쇄)는 이번 범위에서 제외한다 —
   sLLM 단계에서는 1-hop 정확도부터 확인하는 것이 순서다.
3. **`no-tool` 4개는 함정이다.** "서울에서 별 보기 좋은 곳", "제주 흑돼지 맛집",
   "MCP 가 뭐야", "내일 서울 날씨" — 서버 범위 밖이다. 도구를 부르면 감점,
   범위 밖이라고 밝히면 만점.
4. **`evaluate` 8개 중 2개는 미등록 장소**다. 하늘은 판정하되 주차·야간 출입은
   "확인되지 않았다"고 말해야 정답이다 — 모르는 것을 아는 척하지 않는지를 본다.

## 5. 지표 정의

### 5.1 도구 사용 정확도 (arm B 전용)

| 지표 | 정의 | 좋은 방향 |
|---|---|---|
| **TSA** Tool Selection Accuracy | 첫 도구 호출의 이름 == `gold_tool` 인 케이스 비율 (`no-tool` 은 "안 부름"이 정답) | ↑ |
| **AEM** Argument Exact Match | `required_args` 전부가 값까지 일치한 비율 (문자열은 공백 제거 후 비교, 숫자는 정확히) | ↑ |
| **ASF1** Argument Slot F1 | 예측 인자 집합 vs `gold_args` 의 (키,값) 마이크로 F1. 부분 점수용 | ↑ |
| **ICR** Invalid Call Rate | 없는 도구 이름 · JSON 파싱 실패 · 스키마 거부(422) 비율 | ↓ |
| **OTR** Over-Trigger Rate | `no-tool` 케이스에서 도구를 부른 비율 | ↓ |
| **TPQ** Turns per Query | 최종 답까지의 LLM 왕복 수 (이상적 2: 호출 결정 + 답변 생성) | ↓ |

### 5.2 답변 품질 (arm A vs B — **개선폭은 여기서 나온다**)

정답은 arm T 가 `gold_args` 로 도구를 불러 받은 응답이다. 그 응답에서 검증 가능한
값(장소명·주행 분·도보 분·등급·야간 출입 문구)을 뽑아 **gold set** 을 만든다.

| 지표 | 정의 | 좋은 방향 |
|---|---|---|
| **GFR** Grounded Fact Recall | gold set 의 값 중 최종 답변에 실제로 등장한 비율 | ↑ |
| **FNR** Fabricated Number Rate | 답변에 나온 수치 토큰(`분`·`km`·`시`·`등급`·`℃`) 중 gold set 에도 질문에도 없는 것의 비율 = **환각률** | ↓ |
| **PNR** Place-Name Validity | 답변이 추천한 장소명 중 검증된 62곳(또는 실제 제주 지명)에 있는 비율 | ↑ |
| **TSR** Task Success Rate | 케이스별 규칙 체크리스트(필수 사실 전부 포함 & 금지 사실 없음)를 통과한 비율 | ↑ |
| **ABS** Abstention Correctness | `no-tool`·미등록 장소 케이스에서 "모른다/범위 밖"을 밝힌 비율 | ↑ |

**채점은 전부 규칙 기반이다.** LLM 판정자를 쓰지 않는다 — 재현 가능해야 하고,
판정자 모델이 바뀌면 숫자가 흔들리기 때문이다. 규칙이 못 잡는 미묘한 품질 차이는
리포트에 **샘플 답변 원문**을 붙여 사람이 보게 한다.

### 5.3 지연 — **도구 로직 시간을 분리해서 잰다**

이 서버의 도구는 가볍지 않다. 도로 그래프 탐색(`core/routing`)·천문 계산
(skyfield)·광공해 격자(numpy)·외부 기상 API(Open-Meteo)가 한 호출 안에 들어 있다.
그래서 **LLM 이 느린 것과 도구가 느린 것을 반드시 갈라야** 한다.

한 케이스의 벽시계 시간을 이렇게 쪼갠다:

```
t_e2e  =  t_llm  +  t_tool_rtt  +  t_harness
                     └─ t_tool_rtt = t_tool_exec + t_mcp_net
```

| 기호 | 무엇 | 어떻게 재나 |
|---|---|---|
| `t_llm` | LLM 생성 시간 합(모든 턴) | Ollama 응답의 `total_duration` 합 (적재 시간 `load_duration` 은 **뺀다**) |
| `t_tool_exec` | **도구 로직 순수 실행 시간** | arm T 가 같은 인자로 잰 서버측 실행 시간 (동일 인자 3회 중앙값) |
| `t_tool_rtt` | 도구 호출 왕복(클라이언트 기준) | bench 가 MCP `call_tool` 앞뒤로 잰 시간 |
| `t_mcp_net` | 프로토콜·직렬화·컨테이너 간 네트워크 | `t_tool_rtt - t_tool_exec` |
| `t_harness` | 파싱·프롬프트 조립 등 하네스 몫 | `t_e2e - t_llm - t_tool_rtt` |

**보고 규칙 세 가지:**

1. arm A 에는 도구 시간이 없다. 그래서 지연 비교는 **`t_e2e` 와 `t_llm` 을 둘 다**
   싣는다. `t_llm` 비교가 "도구 붙이면 프롬프트가 길어져 추론이 얼마나 느려지나"를,
   `t_e2e` 비교가 "사용자가 실제로 얼마나 더 기다리나"를 답한다.
2. **cold / warm 을 나눈다.** Open-Meteo 응답은 `requests-cache` 로 `.cache` 에
   남고, 도로 그래프·성좌표(de421.bsp)는 프로세스 최초 호출에 적재된다. 첫 호출은
   따로 표시하고, 본 측정은 워밍업 뒤 warm 상태에서 한다.
3. **`t_tool_exec` 은 모델과 무관한 상수**다. 모델별 표에 그대로 실어, 개선 대비
   비용에서 "이만큼은 모델을 바꿔도 안 줄어드는 몫"임을 보이게 한다.

### 5.4 비용

토큰: 케이스별 `prompt_eval_count`(입력) · `eval_count`(출력) 합. 도구 스키마가
프롬프트에 얹히는 값이 얼마인지가 여기서 드러난다. 생성 속도 `eval_count /
eval_duration` (tok/s) 도 함께 싣는다.

## 6. 통제 변수 — 이걸 안 지키면 숫자가 흔들린다

| 항목 | 고정값 | 이유 |
|---|---|---|
| `temperature` | `0` | 재현성 |
| `top_p` / `top_k` | `1.0` / `1` | 그리디 고정 |
| `seed` | `42` | 남는 비결정성 억제 |
| `num_ctx` | `8192` | 도구 스키마(한국어 설명이 길다) + 도구 응답이 들어가야 한다. 모델 간 동일 |
| `num_predict` | `1024` | 답변 잘림 방지 상한 |
| **기준 날짜·시각** | 프롬프트에 `오늘은 2026-08-20 (KST)` 명시 | 이게 없으면 모델마다 `date` 를 제멋대로 넣어 정답이 결정되지 않는다 |
| 케이스 순서 | 고정 (id 순) | 캐시 상태가 arm 간 같게 |
| 반복 | 케이스당 **3회** | 지연은 **중앙값**, 정확도는 3회 다수결이 아니라 **3회 각각을 개별 시행으로** 집계 |
| 워밍업 | 모델·arm 마다 1회 실행 후 폐기 | 모델 적재·도구 cold 를 본 측정에서 제외 |
| GPU 점유 | 호스트 Ollama 는 중지 | 8GB 를 컨테이너가 온전히 쓰게 |

**동시 실행 금지.** 케이스는 전부 직렬로 돈다. 병렬로 돌리면 GPU 경합으로
`t_llm` 이 오염된다.

## 8. 리포트에 반드시 들어갈 것

1. **환경 표** — 커밋 해시, 이미지 다이제스트, GPU/드라이버, 측정 일시, 케이스 수.
2. **모델 × arm 정확도 표** — TSA·AEM·GFR·FNR·TSR, 그리고 **A→B 변화량(Δ)**.
3. **지연 분해 표** — `t_e2e` / `t_llm` / `t_tool_rtt` / `t_tool_exec` / `t_mcp_net` 중앙값과 p95.
4. **도구별 로직 시간** — 3개 도구 × (cold, warm). 모델과 무관한 상수임을 명시.
5. **실패 사례 원문** — 도구 오선택·인자 누락·환각 답변을 모델당 최소 1건씩 그대로.
6. **한계** — 아래 §9 를 그대로 싣는다.

**개선폭 표기 규칙**: 절대 변화(`Δ = B - A`, %p)를 주로 쓴다. 상대 배수는 분모가
0 에 가까울 때(예: 베이스라인 GFR 0%) 무한대로 튀므로, 그 경우 "0% → 78%"처럼
**원값 두 개를 나란히** 적고 배수를 쓰지 않는다.

## 9. 2차 실험 — 도구 설명(tool description) 최적화

1차에서 모델 셋(qwen3.5:4b · gemma4:e2b-it-qat · llama3.1:8b)을 끝까지 재 본 결과,
**같은 서버·같은 도구인데 도구 선택 정확도가 18.1%~100%로 갈렸다**(원자료는
`bench/results/raw_old_prompt/`, 그때 프롬프트가 지금과 달라 지금 결과와 같은 표에
놓지 않는다). 나머지 세 종은 회선이 느려 내려받기가 끝나지 않았다. 그래서 2차는 범위를 좁힌다: **모델은 `qwen3.5:4b` 하나로
고정하고, 바꾸는 것은 도구 설명뿐이다.** 근거는 "도구 선택 실패의 원인이 모델 능력보다
설명 품질인 경우가 많다"는 연구(MCP Tool Description 최적화 · arXiv 증강 도구 설명)다.

### 9.1 비교군

| 판본 | 무엇 | 어디에 있나 |
|---|---|---|
| **V0** | 서버가 지금 주는 설명 그대로 | `modules/routes.py` (운영 코드) |
| **V1** | MAID 구조로 증강한 설명 | `bench/tool_desc_v1.py` |

**서버는 건드리지 않는다.** 하네스가 LLM 에게 넘기는 스키마의 *설명 문자열만* 갈아
끼운다(`Toolbox(variant="v1")`). 판정 로직·응답 형식은 두 판본이 완전히 같으므로,
차이는 오직 "LLM 이 읽는 계약"에서 온다. V1 이 이기면 그때 `routes.py` 로 옮긴다.

**시스템 프롬프트는 세 arm 이 모두 같다.** 그래야 차이가 설명 덕이 된다.

### 9.2 V1 이 적용한 다섯 기법 (MAID)

| 기법 | 이 서버에서 무엇을 했나 |
|---|---|
| 의도 명확화 | 도구마다 `[언제]`·`[다른 도구와]`·`[사전 조건]` 세 줄. 특히 "인자를 하나도 안 줘도 부를 수 있다"를 명시 |
| 인자 타입 주석 | 형식·허용값·기본값·예시를 인자 설명에 인라인 (`region` 은 다섯 값뿐, `time` 은 `HH:MM`, `'밤 10시'→'22:00'`) |
| 상호작용 | `[다음]` — 이 도구 뒤에 어떤 도구를 부르는가 |
| 에러 응답 명세 | `[오류 대처]` — "주소 확인 실패면 좌표로 다시", "spots 가 비면 조건을 풀어 다시" |
| 사용 예시 | `[예시]` — 질문 → 호출 인자 3쌍 |
| 검색 친화 키워드 | 첫 줄에 동의어를 몰아 둔다 (추천·찾기·어디로 갈까 / 별 보여?·괜찮아? / 주차·강아지·야간 출입) |

### 9.3 V1 을 짜면서 깨진 두 가지 (기록해 둔다)

첫 판이 **오히려 나빠졌다** — 도구 호출률이 100%에서 25%로 떨어졌다. 원인 둘:

1. **답 쓰는 법을 도구 설명에 넣었더니 도구를 안 불렀다.** `[응답 작성] map_url 을
   첫 줄에…` 절을 도구 설명에 달자, 모델이 도구를 부르지 않고 바로 답을 썼다.
   → 도구 설명은 *언제 부르는가*의 자리다. *어떻게 답하는가*는 시스템 프롬프트 자리다.
2. **설명 안의 예시 URL 을 그대로 베꼈다.** 형식 예시로 넣은 가짜 주소
   (`…/maps/ab12cd34.html`)가 답에 그대로 나왔다.
   → 예시는 **호출 인자까지만** 든다. 결과값 예시는 넣지 않는다.

또 하나: 설명 길이가 V0 의 3배가 되자 프롬프트가 2,280→4,534 토큰으로 늘고 "부르라"는
신호가 묽어졌다. **증강은 길이가 아니라 구조다.** 최종 V1 은 V0 의 약 1.5배로 맞췄다.

### 9.4 추가 지표 — 지도 주소

도구는 `map_url` 을 최상위 키로 돌려주는데 모델이 답에 싣지 않는 문제가 있었다
(qwen3.5:4b 0/60, llama3.1:8b 4/7). 그래서 세 지표를 더 잰다.

| 지표 | 정의 | 좋은 방향 |
|---|---|---|
| **지도주소 포함** | 도구가 준 `map_url` 이 최종 답변에 그대로 있는 비율 | ↑ |
| **첫 줄에** | 그 주소가 답변 **첫 줄**에 있는 비율 (요청 형식) | ↑ |
| **주소 위조** | 답변에 있는 URL 중 도구가 준 주소가 **아닌** 것의 비율 | ↓ |

> 별개의 운영 문제 하나: `.env` 의 `MAP_BASE_URL` 이 꺼져 있는 ngrok 터널을 가리켜
> 서버가 내보내는 지도 주소가 전부 죽어 있었다(로컬 `/maps/…` 는 200, ngrok 은 연결
> 실패). 측정 동안은 `MAP_BASE_URL=http://127.0.0.1:11000` 으로 컨테이너를 다시 띄웠다.
> 운영에서는 ngrok 컨테이너를 함께 띄우거나 이 값을 살아 있는 주소로 고쳐야 한다.

### 9.5 V1 이 갈린 자리와 V2

V1 측정 결과, **인자는 좋아졌는데 도구 선택이 나빠졌다.**

| 지표 | V0 | V1 | 무엇이 일어났나 |
|---|---|---|---|
| 슬롯 F1 | 0.862 | **0.961** | 인자 주석(형식·허용값·예시)이 먹혔다 |
| 환각 수치 FNR | 1.4% | **0.0%** | 같은 이유 |
| TSA | **100%** | 95.8% | N-01 "서울 남산타워에서 별이 잘 보일까?" 3/3 호출 |
| OTR 과잉호출 | **0%** | 25.0% | 같은 원인 |
| 지도 전달 | **95.0%** | 85.0% | 미등록 장소(E-06·E-07)에서 누락 |

원인은 하나다. **검색 친화 키워드가 재현율을 올리는 대신 정밀도를 깎았다** —
첫 줄에 "별 보여?·괜찮아?·볼 수 있어?"를 몰아 넣자 제주 밖 질문까지 끌어당겼다.

그래서 **V2 = V1 + 경계**다. 바꾼 것은 셋뿐이다.

1. 첫 줄 키워드에 범위를 붙인다 — "**제주도 안의**" 를 앞세운다.
2. 도구마다 **`[부르지 않는 경우]`** 절 — 제주 밖(서울·부산·남산타워), 별 관측과 무관
   (맛집·숙소·렌터카·일반 상식). **음성 예시를 이름까지 적는다.**
3. "결과의 map_url 도 함께 옮긴다 — 미등록이라 '확인되지 않았다'고 답할 때도" 한 줄.

**교훈: 키워드 증강은 경계 명시와 짝으로만 넣는다.** 재현율만 올리면 정밀도가 깎인다.

**결과 — V2 가 모든 축에서 V0 이상이다.**

| 지표 | V0 | V1 | **V2** |
|---|---|---|---|
| TSA 도구선택 | 100.0% | 95.8% | **100.0%** |
| AEM 인자정확 | 100.0% | 95.0% | **100.0%** |
| 슬롯 F1 | 0.862 | 0.961 | **0.961** |
| OTR 과잉호출 | 0.0% | 25.0% | **0.0%** |
| GFR 근거 재현 | 83.1% | 83.6% | **87.3%** |
| FNR 환각 수치 | 1.4% | 0.0% | **0.0%** |
| 장소명 유효 | 87.5% | 80.0% | **88.9%** |
| 지도주소 전달 | 95.0% | 85.0% | **100.0%** |
| 지도주소 위조 | 5.0% | 5.6% | **0.0%** |
| TSR 과제 성공 | 90.3% | 87.5% | **90.3%** |
| 프롬프트 토큰(중앙값) | 6,735 | 8,400 | 9,708 |

값 하나도 V0 보다 나쁘지 않고, 근거 재현·지도 전달·인자 충실도가 올랐다.

> **이 표의 V0 는 오전에 잰 V0 와 다른 서버다.** 세 판본을 재기 직전
> `modules/tools.py` 가 바뀌었다 — 추천 결과의 `reasons` 산문 안에 구름·Bortle 수치를
> 넣는 변경이다(작은 모델이 구조화 배열 `spots[]` 은 잘 안 읽고 산문만 읽는다는,
> 바로 이 측정에서 나온 관찰을 반영한 것). 세 판본은 **전부 그 뒤의 같은 서버**로
> 돌았으므로 서로의 비교는 유효하고, 오전 수치와의 비교는 유효하지 않다. 치른 값은
프롬프트 토큰 +44%(중앙값 6,735→9,708)이고, 지연은 거의 그대로다(t_e2e 중앙값
4.26s→4.09s — 설명이 길어져도 프리필은 GPU 가 금방 먹는다).

## 10. 이 실험이 말하지 못하는 것 (선언)

- **답변의 문장 품질은 재지 않는다.** 규칙 기반 채점은 사실 일치만 본다.
- **다단계 도구 사용은 범위 밖이다.** 1-hop 만 본다.
- **날씨 의존 값은 측정 시점에 묶여 있다.** 구름·시상은 그날 예보라, 며칠 뒤 다시
  돌리면 gold set 자체가 달라진다. 그래서 정답은 **본 측정과 같은 세션에서**
  arm T 로 생성하고, 리포트에 생성 시각을 적는다.
- **모델 순위는 이 도구 셋·이 한국어 스키마 한정**이다. 일반적인 도구 호출 능력
  순위로 읽으면 안 된다.
- **케이스 24개 × 3회 = 시행 72개/arm** 이다. 모델 간 몇 %p 차이는 통계적으로
  유의하지 않을 수 있다. 리포트에는 비율 지표에 **Wilson 95% 신뢰구간**을 함께 적는다.
