목적: `star_research.md`의 복잡한 설계를 **가장 단순한 뼈대에서 시작해 한 축씩 붙여 확장**하도록 재구성한다.

> **이번 갱신 요지**: 2차 수치검증(`star_research_validation2.md`)이 완료됨. 로드맵·고정항목·순서 근거는 그대로 계승하고, **① 검증이 확정한 상수/픽스처를 각 단계 완료 기준에 명시**, **② 검증이 지적한 잔여 이슈(Bará 인용 오귀속·Crumey 6.18 인용·Falchi SQM 참고열 근거) 3건을 해당 단계의 착수 단서로 배치**, **③ 회귀 픽스처를 단계별로 구체화**한 부분만 갱신했다.

## 0. 설계 원칙 — "무엇을 고정하고 무엇을 미루는가"

복잡도를 줄이는 핵심은 기능을 빼는 게 아니라 **순서를 정하는 것**이다. 아래 3가지는 **1단계부터 고정**하고, 나머지는 전부 나중에 붙인다.

### 고정 1 — 진입점은 하나, 평가 엔진도 하나
문서의 결론(`star_research.md` 141행)대로 **엔진은 공유하고 진입점만 다르게** 둔다. 처음엔 `evaluate_spot` 하나만. `find_spots`·`tonight_sky`는 같은 엔진을 재사용하는 껍데기이므로 나중에 추가해도 구조가 안 흔들린다.

### 고정 2 — 응답 스키마는 1단계부터 최종형
값이 하드코딩이라도 응답 모양은 처음부터 최종형으로 둔다. 나중에 필드 추가는 쉽지만 구조 변경은 어렵다.

```jsonc
{
  "verdict": "관측 양호",          // 한 줄 결론
  "reasons": ["...", "..."],       // 사람이 읽는 근거
  "numbers": { "sqm": 21.2, ... }, // 구조화 수치 (LLM이 지어내지 못하게 분리)
  "attribution": ["..."],          // 최상위, 축약·생략 금지
  "as_of": "2026-07-24T20:00+09:00"
}
```

### 고정 3 — 요인(factor)은 플러그인, 데이터는 provider
각 방해 요인(어둡기·달·구름·습도…)을 **독립 모듈**로 두고, 엔진은 그것들을 **합산하기만** 한다. 새 축을 붙이는 것 = 파일 하나 추가 + 등록 한 줄. 이게 "하나씩 덧붙인다"를 코드로 보장하는 장치다.

```
server/
  mcp_server.py            # /mcp 엔드포인트, stateless, 도구 등록
  tools/
    evaluate_spot.py       # 1단계: 이것만
    find_spots.py          # 7단계에 추가
    tonight_sky.py         # 5단계에 추가
  engine/
    evaluate.py            # 공유 오케스트레이터: factor들을 불러 합산
    factors/               # ← 여기에 파일을 "하나씩" 추가하며 확장
      darkness.py          # 1단계
      observing_window.py  # 2단계
      moon.py              # 2·3단계
      limiting_mag.py      # 3단계
      starcount.py         # 3단계 (주 출력)
      cloud.py             # 4단계
      catalog.py           # 5단계
      azimuth_profile.py   # 6단계
  providers/               # 데이터 접근 추상화 (계층 T0/T1/T2 숨김)
    sky_brightness.py      # GeoTIFF 1픽셀
    ephemeris.py           # Skyfield + de421
    star_catalog.py        # BSC5 / OpenNGC
    weather.py             # Open-Meteo (배치파일 읽기)
    viirs.py
    geocode.py
  schema/response.py       # verdict/reasons/numbers/attribution
data/                      # T0·T1 파일 (as_of 포함)
batch-worker/              # 4단계에서 분리 (외부 통신 격리)
```

**엔진 인터페이스 (1단계에 확정, 이후 불변)**
```python
# 각 factor는 이 형태만 지킨다
def contribute(ctx) -> Contribution:
    # ctx: 좌표·시각·앞 factor들의 누적 결과
    # return: 하늘밝기 기여 / 판정 기여 / numbers 조각 / attribution
    ...
```
엔진은 factor 리스트를 순서대로 돌며 결과를 누적할 뿐이다. → **factor를 늘려도 엔진 코드는 안 바뀐다.**

## 2. 단계별 상세

### P0 — 걷는 뼈대 (Walking skeleton)
**목표**: 좌표를 넣으면 고정 스키마로 응답하는 MCP 서버.
- Streamable HTTP 단일 엔드포인트 `/mcp`, **stateless**(세션·`Mcp-Session-Id` 미사용)
- 도구 `evaluate_spot(lat, lon, date)` — 좌표 직접만. 지오코딩·지명 입력 없음
- 응답은 하드코딩이라도 `verdict/reasons/numbers/attribution/as_of` 완비
- 입력 검증: 제주 범위(위도 33.1–33.6, 경도 126.1–127.0) 밖이면 에러 메시지도 프롬프트로
- **완료 기준**: MCP 클라이언트가 도구를 호출해 스키마 응답 수신

### P1 — 어둡기 한 축 (장소의 고정 속성)
**목표**: "이 지점이 얼마나 어두운가"를 실제 데이터로 답한다.
- `providers/sky_brightness.py`: GeoTIFF(`data/*.tif`) 1픽셀 조회, **nodata −999.9 마스킹 필수**
- `factors/darkness.py`:
  - `SQM = log10((인공밝기 + 0.171168465) / 1.08e8) / −0.4`
  - Falchi 등급(비율 기준) — 주 기준. Bortle은 보조 병기
  - 단위 주의: 팝업 μcd/m² vs GeoTIFF mcd/m² (1000배)
- **영점·자연광 상수를 한 쌍으로 고정**(1.08e8 ↔ 0.171168465). 혼용 금지
- **완료 기준(회귀 픽스처 — 검증 확정값)**: 문서 예시 지점을 고정 픽스처로 박는다.
  - 용눈이오름 SQM 21.2 → 인공/자연 비율 1.06 → **Falchi 등급 iv**
  - 제주 p95 21.86 → 비율 0.12 → **iii** / p50 21.50 → 0.56 → **iv** / 제주시 19.14 → 12.7 → **v**
  - 단위 검산 픽스처: Ratio 0.594/0.171168465 = 3.47 (팝업 μcd ↔ GeoTIFF mcd 1000배)
  - 이 값들은 2차 검증에서 **✅ 일치**(비율은 영점 무관 불변)로 확정됨. 이때부터 실사용 가치 발생

> **검증 반영(P1 착수 단서)** — `star_research_validation2.md` 확정. 대부분 ✅이나 표기 정정 2건을 P1 구현 시 함께 반영:
> - **Bará 인용 오귀속(❌)**: 영점 1.08e8의 "9550 K 흑체·Johnson V 밴드" 전제의 실제 출처는 **Bará, Aubé, Barentine & Zamorano 2020, MNRAS 493, 2429 (DOI 10.1093/mnras/staa323)**. 문서의 "Bará 2017, MNRAS 471, 4164"는 오귀속. attribution 문자열에 올바른 서지를 넣는다. (계산값은 안 바뀜 — 표기만)
> - **Falchi SQM 참고열 근거(🟡)**: Falchi 등급표의 SQM 참고열(21.97/21.90/…)은 본문 서술("Falchi 174 μcd/m² 기준 환산")과 달리 **프로젝트 영점 1.08e8로 계산**된 값(차이 0.02 mag). 판정은 비율로 하므로 결과 불변이나, 참고열 캡션을 "프로젝트 영점 환산"으로 정정한다.

### P2 — 시간 축 (문서가 말한 진짜 가치의 절반)
**목표**: "오늘 밤 몇 시부터 몇 시까지, 달은 얼마나 방해되나".
- `providers/ephemeris.py`: Skyfield + de421.bsp (로컬 17MB, 오프라인)
- `factors/observing_window.py`: 천문박명(−18°) 이분탐색 → 관측 창
- `factors/moon.py` (1부): 달 조도(`fraction_illuminated`), 월몰 시각, 달 고도·방위
- 아직 달빛의 **밝기 기여 계산은 안 함**(P3에서). 여기선 "달이 몇 시에 지고 얼마나 밝은지"만
- **완료 기준**: "관측 창 21:20~03:58, 조도 31%, 월몰 22:43, 22:43 이후 최적" 형태 출력

### P3 — ★ 별 개수 (주 출력, 핵심 완성점)
**목표**: 문서의 주 출력 "오늘 밤 별 약 N개"를 완성한다.
- `factors/moon.py` (2부): K&S(1991) 달빛 산란 → 총 하늘 밝기에 합산
  - 식 (1)(2)(3)(15)(19)(20)(21). **식(2) 천정거리 보정 누락 금지**
  - 소광계수 k=0.33 기본(조정 가능 파라미터)
- `factors/limiting_mag.py`: Crumey(2014) 한계등급, F=2 기본
- `factors/starcount.py`: BSC5로 한계등급 이하 별 수 계산 → **주 출력**
- 출력에 **"무엇이 깎았나"**(달빛/광공해 기여분) 분해 표기
- **완료 기준(회귀 픽스처 — 검증 확정값)**: 문서 d-2)·d)절의 값을 그대로 픽스처로 고정.

  | 하늘 SQM | m₀ (Crumey, F=2) | 고도 10°↑ 보이는 별 |
  | --- | --- | --- |
  | 21.9 (제주 최상급) | 6.20 | 2,468개 |
  | 21.5 (제주 중앙값) | 6.05 | 2,094개 |
  | **21.2 (용눈이오름)** | **5.94** | **1,847개** |
  | 20.0 (반달) | 5.48 | 1,087개 |
  | 19.1 (제주시) | 5.22 | 828개 |

  - 요인 배수 픽스처: 장소 2.9배, **달 2.7배**, 어두운 지점끼리 1.3배 (문서 표 그대로)
  - 출력 예시 "약 1,600개 · 달빛 −170 · 광공해 −560" 형태. **이 단계에서 서비스의 핵심 질문에 답 완료**
  - 위 점광원열 m₀는 2차 검증에서 **✅ 자기정합·재현 일치**로 확정됨(Crumey Eq.54, F=2).

> 문서 우선순위: 여기까지가 가치의 대부분. P4 이후는 정밀도·부가정보.

> **검증 반영(P3 착수 단서)** — K&S·Crumey 계열은 대부분 ✅이나 잔여 ⚠️/❌를 아래처럼 취급하고 **구현은 진행**한다(형태·검산 정합 확인됨):
> - **Crumey "F=2 (limit 6.18 mag)" 인용(❌/🟡)**: 문서가 인용부호로 적은 6.18은 자기 식(Eq.54)을 μ=22.0에 대입한 값(6.22~6.24)과 상충하며 6.18은 μ≈21.8에 해당. **픽스처는 인용문 6.18이 아니라 자기정합값(SQM 21.9→6.20, 22.0→6.22)을 채택**한다. 원문 전문 확보 시 인용 문구만 정정.
> - **K&S 식(2)(15)(19) 절대상수**(⚠️, 1차 전문 미열람): 식(20)(21)·정확도 8~23%·k=0.172는 교차확인됨. 구현은 문서 구현식대로 진행하되 **식(2) 천정거리 보정 누락 금지**를 회귀 테스트로 강제.
> - 보름달 근처(|α|<7°) 정확도 저하는 K&S 원문 명시 한계 — 결과 문구에 반영.

### P4 — 구름 (유일한 실시간 축, go/no-go)
**목표**: "그래서 오늘 볼 수 있나".
- `batch-worker` 컨테이너 분리: Open-Meteo 3시간 배치 → `data/weather_*.json`
- MCP 서버는 **파일만 읽음**(egress 0 유지)
- `factors/cloud.py`: 차폐율 `1−(1−C_low)(1−C_mid)`, 고층운 별도 표시
- **구름층 경계는 Open-Meteo 정의 확정값**(3km / 3–8km / 8km~). `cloud_cover_low`는 **안개 포함** — 이슬점 판정과 겹치면 "저층운/안개"로 통합 (fixes.md F3, 검증 ✅)
- 강수·습도·이슬점·풍속 임계는 **운영 기준으로 명시**(문헌 상수 아님)
- 구름 차폐를 별 개수에 선형 반영(차폐율 → 개수 감소)
- **완료 기준(회귀 픽스처)**: 용눈이오름 케이스 저층 5%/중층 10%/고층 25% → **차폐율 14.5%**(관측 가능), 고층운 25% 별도 표시. 광학두께→투과율 검산(τ<0.03→97%, 0.03~0.3→74%)은 검증 ✅
- 관측 창 시간별 구름 + go/no-go 1차 판정

### P5 — 천체 목록 + 별자리 (`tonight_sky` 도구 등장)
**목표**: "뭐가 보이나" — 부가 기능이지만 발표 임팩트 큼.
- `providers/star_catalog.py`: OpenNGC(pyongc), de421 행성
- `factors/catalog.py`: **점광원/확산천체 2조건** 필터
  - 점광원: `V ≤ m₀`
  - 확산천체: `V ≤ m₀ AND μ_V ≤ m₀ + sup(SQM)`
  - 면밝기 `μ_V = V + 2.5log10(π/4·a·b)` (SurfBr 필드 쓰지 말 것 — B밴드·은하 전용)
- 별자리 그룹핑(바이어 명명법, 별도 파일 불필요)
- **새 진입점** `tonight_sky(lat, lon, date)` = 엔진에서 장소평가 빼고 천체목록만
- **완료 기준**: "거문고자리 북동 83°, M39/M24…" + 경계대상 "조건 좋으면 가능" 표기

### P6 — 방위 프로파일 (어느 방향)
**목표**: "오늘 밤 어느 쪽이 어두운가".
- `providers/viirs.py` + `factors/azimuth_profile.py`
- 반경 30km, 16방위, 섹터점수 `Σ Vᵢ/(dᵢ^p + ε)`, ε=0.01
- **p 전구간 스캔**(2~3.33) → 이동 ≤1섹터면 단일방위, 아니면 강건집합
- 대기량 고도가중 `X=(1−0.96sin²z)^−0.5` (K&S, 산란광용)
- **대기량 표 확정값(fixes.md F2, 검증 ✅ 전부 일치)**: 90°→1.00 / 60°→1.15 / 40°→1.51 / 30°→1.89 / **25°→2.17** / 20°→2.56 / 10°→3.81 를 회귀 픽스처로. (구식 결과 예시의 "2.4"는 폐기 — K&S식은 25°에서 2.17)
- VIIRS는 방위집계 전용(절댓값 신뢰 안 함). 보유 래스터는 재샘플링 파생물(0<v<0.5 픽셀 4.8% 존재)이라 픽셀 절댓값 불신 원칙 강화 (F14, 검증 ⚠️→방위집계로 회피)
- p 스캔 픽스처: 42% 불안정 사례(성산일출봉·산굼부리 등 5/12지점) 재현 확인
- **완료 기준**: "WSW 가장 어두움, p 전구간 안정" 또는 "방위 차 불명확"

### P7 — 후보 탐색 (`find_spots` 도구)
**목표**: "이 근처 어디가 좋나".

## 3. 왜 이 순서인가

1. **P1(어둡기)이 먼저인 이유**: 장소의 고정 속성이라 실시간 의존이 없어 가장 단순. 한 픽셀 조회로 즉시 가치 발생.
2. **P2·P3(시간·별개수)이 그다음인 이유**: 문서가 측정한 영향력 — 달 2.7배 > 장소 1.3배. **가장 큰 변동 요인을 핵심부에 배치**.
3. **P6(방위)을 뒤로 미룬 이유**: p 불안정(42%)이 있지만 방위 미세순위는 원래 영향이 작은 축(문서 933행). 비치명적이므로 후순위.
4. **P4(구름)을 별 개수 뒤에 둔 이유**: 유일한 실시간 축이라 배치워커·캐시 인프라가 필요. 핵심 로직(P3) 완성 후 인프라를 붙이는 게 안전.
5. **도구 3개를 한 번에 안 만드는 이유**: `find_spots`·`tonight_sky`는 `evaluate_spot` 엔진의 재사용. 엔진이 검증된 뒤(P3~) 껍데기만 추가.
