## 0. 설계 원칙 — 무엇을 고정하고 무엇을 미루는가

복잡도를 줄이는 핵심은 기능을 빼는 게 아니라 **순서를 정하는 것**이다. 아래 둘은 첫 단계부터
고정했고 지금까지 유효하다.

### 고정 1 — 진입점은 여럿, 평가 엔진은 하나

엔진은 공유하고 진입점만 다르게 둔다. `evaluate_place` 는 지오코딩 후 좌표 코어(`_evaluate`)를
그대로 공유하고, `find_spots`(P6)도 같은 엔진을 후보에 반복 적용하는 껍데기가 된다.

### 고정 2 — 응답 스키마는 첫 단계부터 최종형

값이 하드코딩이라도 응답 모양은 처음부터 최종형으로 둔다. 필드 추가는 쉽지만 구조 변경은 어렵다.

```jsonc
{
  "verdict": "관측 양호",          // 한 줄 결론
  "reasons": ["...", "..."],       // 사람이 읽는 근거
  "numbers": { "sqm": 21.2, ... }, // 구조화 수치 (LLM이 지어내지 못하게 분리)
  "attribution": ["..."],          // 최상위, 축약·생략 금지
  "as_of": "2026-07-24T20:00+09:00",
  "resolved": null                 // 지오코딩 해석 위치. 키는 항상 존재
}
```

### 고정 3 (변경됨) — 계층은 "요인/데이터"가 아니라 "순수함수/네트워크"

> 초기 계획은 `factors/` · `providers/` 에 `contribute(ctx) -> Contribution` 플러그인
> 인터페이스를 두는 구조였다. **채택하지 않았다** — 그 역할을 LangGraph 노드 + 리듀서가
> 그대로 수행하기 때문이다. 자세한 경위는 `decisions.md` §2.4.

현재 구조:

```
server/
  mcp_server.py       # /mcp 엔드포인트, stateless, 도구 등록
  schema.py           # 응답 스키마 (고정 2)
  path.py             # 모든 데이터 경로 상수
  core/               # 순수 함수 — 네트워크·LLM 호출 금지
    astro.py          #   박명 구간 (DE421)
    judge.py          #   한 시각 등급 판정
    darkness.py       #   광공해 SQM·Falchi
    tonight.py        #   밤 단위 집계
  clients/            # 외부 I/O — 예외를 밖으로 던지지 않는다
    open_meteo.py
    geocode.py
  engine/
    graph.py          # LangGraph 조립 + run / run_tonight
    state.py          # 공유 상태 + 리듀서
scripts/              # 오프라인 배치 (연 1회 래스터 전처리 등)
data/                 # 정적 데이터 (.py 없음)
```

**축을 늘리는 방법**은 그대로다 — `core/` 에 파일 하나 추가 + `graph.py` 에 노드·엣지 한 줄.
`darkness_node` 가 그렇게 붙었다.

## 1. 완료된 단계 — 무엇으로 완료 판정했나

### P0 — 걷는 뼈대 ✅
- Streamable HTTP 단일 엔드포인트 `/mcp`, **stateless**(`Mcp-Session-Id` 미사용)
- 응답은 하드코딩이라도 `verdict/reasons/numbers/attribution/as_of` 완비
- 제주 범위 밖이면 **에러 메시지도 프롬프트형**으로
- **완료 기준**: MCP 클라이언트가 도구를 호출해 스키마 응답 수신 ✅

### P1 — 시간 축 (박명) ✅
- `core/astro.py`: Skyfield + `de421.bsp`(로컬, 오프라인). `dark_twilight_day` 로 태양 고도
  구간 0~4 를 **가공 없이** 노출
- `twilight_state()` / `dark_window()`(완전한 밤) / `night_window()`(박명 포함 밤, < −6°)
- **완료 기준**: 박명 단계별 등급 상한이 judge 에 반영, `time` 파라미터로 임의 시각 평가 ✅

### P2 — 지명 입력 ✅
- `clients/geocode.py`: Photon(키 불필요, OSM 기반). 제주 bbox 편향 + 알려진 접두 지역어 제거 fallback
- 끝/첫 토큰을 임의로 떼는 축약은 **쓰지 않는다** — '성산일출봉 없는장소' → '성산일출봉' 처럼
  존재하지 않는 질의를 엉뚱한 실제 장소로 확정시킨다
- 못 찾으면 `None` → 좌표 탐색은 Host LLM 몫 (MCP 표준, 서버 간 결합 회피)
- **완료 기준**: `evaluate_place('성산일출봉')` 이 좌표로 해석돼 동일 코어를 태움 ✅

### P3 — 구름 축 ✅
- `clients/open_meteo.py`: judge 가 실제로 소비하는 값만 요청 — `cloud_cover`·`visibility`
- `fetch(when)` / `fetch_series(start, end)`(밤 구간을 **한 번의 호출로**)
- **총운량 단일 축**. 층별 차폐율은 채택하지 않았다 (`decisions.md` §2.1)
- **완료 기준(회귀 픽스처)**: 경계값 10.0 / 30.0 / 50.0 이 각각 최적 / 양호 / 밝은 별 한정으로
  떨어질 것(`_EPS` 로 부동소수점 경계 보호). 결측은 '불가'가 아니라 **'알 수 없음'** ✅

### P4 — 밤 집계 ✅
- `core/tonight.py`: `night_window` 의 매 정시를 judge 로 판정해 집계
- `summarize()` → `observable_hours` · `by_grade` · `photometric_hours`/`spectroscopic_hours`
  (PTB/STB, 순수 운량 기준) · `windows` · `unknown_hours`
- **3시간 기준으로 가능/불가를 매기지 않는다** (`decisions.md` §2.6)
- `scope="night"` 파라미터로 진입 — 별도 도구를 만들지 않았다 (`decisions.md` §2.5)
- **완료 기준**: PTB ⊂ STB 불변식, 창 밖 정시 미포함, 0시간도 '불가'가 아닌 사실 서술 ✅

### P5 — 어둡기 축 (광공해) ✅
- `scripts/build_darkness_grid.py`(전처리, 연 1회) → `core/darkness.py`(런타임, numpy만)
- **nodata −999.9 마스킹 필수**. 격자 밖·해상은 `None` → "데이터 없음"
- 영점·자연광 상수를 **한 쌍으로 고정**(1.08e8 ↔ 0.171168465). 혼용 금지
- verdict 등급은 바꾸지 않고 **은하수 문구만** 정정 (judge 는 장소를 모르는 순수 함수로 유지)
- **완료 기준(회귀 픽스처)**: 용눈이오름 SQM 21.19 → Falchi iv / 제주시 SQM 19.18 → Falchi v ·
  Bortle 6 / 격자 분포 min 19.14 · p50 21.50 · max 21.93 ✅
- attribution 은 **Black Marble / LPM 귀속**을 축어로 (Falchi 인용이 아니다) ✅

## 2. 다음 단계 — 착수 조건과 완료 기준

### P6 — 관측지 탐색 (`find_spots`)  ← 다음

**목표**: "이 근처 어디가 좋나".

- **관측지 크롤링**으로 후보를 확장한다. 현재 `data/jeju_spots.json` 20곳은 관광공사·비짓제주·
  위키·문화대전 교차확인 큐레이션이며 **엔진 미연결 참고자료** 상태다
- 크롤링 결과와 큐레이션을 합쳐 후보 풀 구성 → 어둡기(SQM) 기준 랭킹 → top N 출력
- 필터: 바다·시설 없음·출입 제한 지점 제외
- **불투명 커서** 페이지네이션 (stateless, 세션 저장 안 함)
- **착수 조건**: 없음. 어둡기 축(P5)만으로 점수가 나온다
- **완료 기준**: 중심좌표 + 반경 → 랭킹된 관측지 목록 + 다음 커서. 각 항목이 기존 응답
  스키마(`numbers` 에 sqm·falchi)를 그대로 실을 것

> **순서를 바꾼 이유**: 초기 계획은 이 단계(구 P7)를 별 개수 뒤에 뒀다. 하지만 랭킹은 지금
> 있는 어둡기 축만으로 동작하므로, 데이터를 먼저 불리고 점수 기준은 나중에 승격한다.

### P7 — 별 개수 (달빛 · 한계등급 · 성표)

**목표**: "오늘 밤 별 약 N개".

- **달** — K&S(1991) 달빛 산란을 총 하늘 밝기에 합산. 식 (1)(2)(3)(15)(19)(20)(21).
  **식(2) 천정거리 보정 누락 금지** — 회귀 테스트로 강제한다. 소광계수 k=0.33 기본(조정 가능)
- **한계등급** — Crumey(2014), F=2 기본
- **별 수** — BSC5 로 한계등급 이하 별 수 계산
- 출력에 **"무엇이 깎았나"**(달빛/광공해 기여분) 분해 표기
- **완료 기준(회귀 픽스처)**

  | 하늘 SQM | m₀ (Crumey, F=2) | 고도 10°↑ 보이는 별 |
  |---|---|---|
  | 21.9 (제주 최상급) | 6.20 | 2,468 |
  | 21.5 (제주 중앙값) | 6.05 | 2,094 |
  | **21.2 (용눈이오름)** | **5.94** | **1,847** |
  | 20.0 (반달) | 5.48 | 1,087 |
  | 19.1 (제주시) | 5.22 | 828 |

  요인 배수: 장소 2.9배 · **달 2.7배** · 어두운 지점끼리 1.3배

- **착수 단서 (인용 주의)**
  - Crumey 의 "F=2 (limit 6.18 mag)" 인용은 자기 식(Eq.54)을 μ=22.0 에 대입한 값(6.22~6.24)과
    상충한다(6.18 은 μ≈21.8 에 해당). **픽스처는 인용문 6.18 이 아니라 자기정합값**
    (SQM 21.9→6.20, 22.0→6.22)을 쓴다
  - K&S 식(2)(15)(19)의 절대상수는 1차 전문 미열람 상태다. 식(20)(21)·정확도 8~23%·k=0.172 는
    교차확인됨 — 형태·검산이 정합하므로 구현은 진행한다
  - 보름달 근처(|α| < 7°) 정확도 저하는 K&S 원문 명시 한계 — **결과 문구에 반영**

> 초기 계획에서 별도 단계였던 "달 조도·월몰만 내보내기"는 두지 않는다. 달빛의 밝기 기여
> 계산 없이 월몰 시각만 주는 중간 산출물은 판정에 쓰이지 않기 때문이다.

## 3. 이후 단계

### P8 — 천체 목록
- OpenNGC(pyongc) + de421 행성. 한계등급(P7)을 재사용한다
- **점광원/확산천체 2조건** 필터 — 점광원 `V ≤ m₀`, 확산천체 `V ≤ m₀ AND μ_V ≤ m₀ + sup(SQM)`
- 면밝기 `μ_V = V + 2.5·log10(π/4·a·b)`. **SurfBr 필드를 쓰지 말 것** (B밴드·은하 전용)
- **완료 기준**: "거문고자리 북동 83°, M39/M24…" + 경계 대상은 "조건 좋으면 가능" 표기

### P9 — 방위 프로파일
- VIIRS 야간광. 반경 30km, 16방위, 섹터 점수 `Σ Vᵢ/(dᵢ^p + ε)`, ε=0.01
- **p 전구간 스캔**(2~3.33) → 이동 ≤1섹터면 단일 방위, 아니면 강건 집합
- 대기량 고도 가중 `X = (1 − 0.96·sin²z)^−0.5` (K&S, 산란광용)
- **완료 기준(회귀 픽스처)** — 대기량: 90°→1.00 / 60°→1.15 / 40°→1.51 / 30°→1.89 /
  **25°→2.17** / 20°→2.56 / 10°→3.81
- VIIRS 는 **방위 집계 전용**(절댓값 신뢰 안 함). 보유 래스터는 재샘플링 파생물이라
  (0<v<0.5 픽셀 4.8% 존재) 픽셀 절댓값 불신 원칙을 유지한다
- p 스캔 픽스처: 12지점 중 5지점(42%) 불안정 사례 재현 (성산일출봉·산굼부리 등)
- **완료 기준**: "WSW 가장 어두움, p 전구간 안정" 또는 "방위 차 불명확"

### P10 — 접근성·안전
- OSM POI(주차·휴게소·전망대), 야간 출입, ITS 도로 상태·결빙, 여성밤길치안안전 API
- 3단계 판정 🟢🟡🔴. 규제 blocklist 는 **수동 검토**(자동 반영 금지)
- `priority = darkness|safety|balanced` 파라미터

### P11 — 배포 (`egress 0` 복원)
- Docker / docker-compose
- `batch-worker` 분리: Open-Meteo 를 배치로 받아 파일로 떨구고 MCP 서버는 **파일만 읽음**
- 현재는 서버 직접 호출 + `requests_cache`(1h). 경위는 `decisions.md` §2.9

### P12 — 지형 개활도
- Copernicus GLO-30 DEM 으로 방위별 지평선 프로파일
- 현재의 **하한 10° 일괄**을 방위별 정밀 차폐로 승격

## 4. 왜 이 순서인가

1. **어둡기(P5)를 실시간 축보다 먼저** 끝낸 이유: 장소의 고정 속성이라 실시간 의존이 없고,
   한 픽셀 조회로 즉시 가치가 난다.
2. **지오코딩(P2)이 앞으로 온 이유**: 계획은 뒤(구 P8)에 뒀지만, 좌표를 직접 넣는 것보다
   지명을 넣는 게 실사용 진입 장벽을 훨씬 크게 낮춘다. 구현 비용도 작았다.
3. **탐색(P6)이 별 개수(P7)보다 먼저인 이유**: 랭킹은 어둡기 축만으로 동작한다. 데이터를
   먼저 불려 놓고, 점수 기준을 나중에 별 개수로 승격하는 편이 각 단계가 더 완결적이다.
4. **방위(P9)를 뒤로 미룬 이유**: p 불안정(42%)이 있지만 방위 미세 순위는 원래 영향이 작은
   축이다. 비치명적이므로 후순위.
5. **도구를 한 번에 안 만드는 이유**: 진입점은 같은 엔진의 껍데기다. 엔진이 검증된 뒤
   껍데기만 추가한다.
