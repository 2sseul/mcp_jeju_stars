## 0. 제품 정의 — 누가 무엇을 묻는가

초기 계획은 **"이 좌표·이 시각에 별이 보이나"** 를 답하는 판정 엔진이었다. 실제 사용자를
제주 관광객으로 좁히면서 질문이 바뀌었다.

> **"지금(또는 오늘 밤), 내가 갈 수 있는 거리 안에서 어디로 갈까"**

바뀐 전제:

| | 초기 | 현재 |
|---|---|---|
| 사용자 | 불특정 | **제주 관광객** — 자기 위치를 모르고, 왕복 1시간 이내를 선호하며, 초행·야간 운전이다 |
| 주 진입점 | `evaluate_place` (단일 장소 판정) | **추천**(`find_spots`). 단일 장소 판정은 "추천받은 곳을 확인하는" 보조로 내려간다 |
| 산출물 | 등급 + 근거 | 등급 + 근거 + **주차·화장실·주의사항·길찾기·지도** |
| 날씨의 지위 | 판정의 게이트 | 게이트는 **밤 전체**에만. 장소별로는 순위를 가르는 축 |

여기서 따라 나오는 것들:

- **후보 풀이 곧 제품이다.** 큐레이션 20곳으로는 "숙소 근처"를 못 답한다. 유명 관측지는
  관광지라서 유명하고, 관광지에는 조명·주차장이 있어 정의상 덜 어둡다. 진짜 어두운 지점은
  이름이 없다 → 자동 발굴이 필요하다 (P9).
- **추천은 안전 문제다.** 관광객이 초행길에 밤에 간다. 격자에서 뽑은 좌표가 사유지 농로·
  묘지·갓길 없는 절개지일 수 있다. 자동 발굴 결과를 그대로 내보내지 않고 **로드뷰 데스크
  전수 검증**을 통과한 것만 노출한다.
- **주차 지점과 관측 지점은 다르다.** 주차장에는 가로등이 있어 어둡기 점수를 갉아먹는다.
  좌표를 하나로 두지 않고 `(주차 좌표, 관측 좌표, 도보 소요시간, 도보 유형)` 으로 나눈다.
- **정체를 따지지 않는다** — 별을 보러 가는 시각은 밤~심야다. 그래서 주행시간을 정적
  도로망만으로 계산할 수 있고, 실시간 교통 API 없이 `egress 0` 방침을 깨지 않는다.

## 1. 설계 원칙 — 무엇을 고정하고 무엇을 미루는가

복잡도를 줄이는 핵심은 기능을 빼는 게 아니라 **순서를 정하는 것**이다. 아래 둘은 첫 단계부터
고정했고 지금까지 유효하다.

### 고정 1 — 진입점은 여럿, 평가 엔진은 하나

엔진은 공유하고 진입점만 다르게 둔다. `evaluate_place` 는 지오코딩 후 좌표 코어(`_evaluate`)를
그대로 공유하고, `find_spots`(P10)도 같은 엔진을 후보에 반복 적용하는 껍데기가 된다.

### 고정 2 — 응답 스키마는 첫 단계부터 최종형

값이 하드코딩이라도 응답 모양은 처음부터 최종형으로 둔다. 필드 추가는 쉽지만 구조 변경은 어렵다.

```jsonc
{
  "verdict": "관측 양호",          // 한 줄 결론
  "reasons": ["...", "..."],       // 사람이 읽는 근거
  "numbers": { "sqm": 21.2, ... }, // 구조화 수치 (LLM이 지어내지 못하게 분리)
  "attribution": ["..."],          // 최상위, 축약·생략 금지
  "as_of": "2026-07-24T20:00+09:00",
  "resolved": null                 // 지오코딩 해석 위치. 키는 항상 존재
}
```

> 추천(P10)에서 **`spots` 배열이 추가**된다. 최상위 필드는 그대로 두고 목록만 얹는 형태다 —
> 전체 스키마는 §3 P10 을 본다.

### 고정 3 (변경됨) — 계층은 "요인/데이터"가 아니라 "순수함수/네트워크"

> 초기 계획은 `factors/` · `providers/` 에 `contribute(ctx) -> Contribution` 플러그인
> 인터페이스를 두는 구조였다. **채택하지 않았다** — 그 역할을 LangGraph 노드 + 리듀서가
> 그대로 수행하기 때문이다. 자세한 경위는 `decisions.md` §2.4.

현재 구조:

```
server/
  mcp_server.py       # /mcp 엔드포인트, stateless, 도구 등록
  schema.py           # 응답 스키마 (고정 2)
  path.py             # 모든 데이터 경로 상수
  core/               # 순수 함수 — 네트워크·LLM 호출 금지
    astro.py          #   박명 구간 (DE421)
    judge.py          #   한 시각 등급 판정
    darkness.py       #   광공해 SQM·Falchi + 3신호 종합 점수
    nightlight.py     #   VIIRS 근거리 광원
    lamps.py          #   가로등·보안등 근접도
    cloud.py          #   위성 구름 마스크 → 운량 비율 → CloudRank (P7)
    tonight.py        #   밤 단위 집계
  clients/            # 외부 I/O — 예외를 밖으로 던지지 않는다
    open_meteo.py
    geocode.py
    gk2a.py           #   천리안 2A 위성 기상산출물 (P7)
  engine/
    graph.py          # LangGraph 조립 + run / run_tonight
    state.py          # 공유 상태 + 리듀서
scripts/              # 오프라인 배치 (연 1회 래스터 전처리 등)
data/                 # 정적 데이터 (.py 없음)
```

**축을 늘리는 방법**은 그대로다 — `core/` 에 파일 하나 추가 + `graph.py` 에 노드·엣지 한 줄.
`darkness_node` 가 그렇게 붙었다.

## 2. 완료된 단계 — 무엇으로 완료 판정했나

### P0 — 걷는 뼈대 ✅
- Streamable HTTP 단일 엔드포인트 `/mcp`, **stateless**(`Mcp-Session-Id` 미사용)
- 응답은 하드코딩이라도 `verdict/reasons/numbers/attribution/as_of` 완비
- 제주 범위 밖이면 **에러 메시지도 프롬프트형**으로
- **완료 기준**: MCP 클라이언트가 도구를 호출해 스키마 응답 수신 ✅

### P1 — 시간 축 (박명) ✅
- `core/astro.py`: Skyfield + `de421.bsp`(로컬, 오프라인). `dark_twilight_day` 로 태양 고도
  구간 0~4 를 **가공 없이** 노출
- `twilight_state()` / `dark_window()`(완전한 밤) / `night_window()`(박명 포함 밤, < −6°)
- **완료 기준**: 박명 단계별 등급 상한이 judge 에 반영, `time` 파라미터로 임의 시각 평가 ✅

### P2 — 지명 입력 ✅
- `clients/geocode.py`: Photon(키 불필요, OSM 기반). 제주 bbox 편향 + 알려진 접두 지역어 제거 fallback
- 끝/첫 토큰을 임의로 떼는 축약은 **쓰지 않는다** — '성산일출봉 없는장소' → '성산일출봉' 처럼
  존재하지 않는 질의를 엉뚱한 실제 장소로 확정시킨다
- 못 찾으면 `None` → 좌표 탐색은 Host LLM 몫 (MCP 표준, 서버 간 결합 회피)
- **완료 기준**: `evaluate_place('성산일출봉')` 이 좌표로 해석돼 동일 코어를 태움 ✅

### P3 — 구름 축 (예보) ✅
- `clients/open_meteo.py`: judge 가 실제로 소비하는 값만 요청 — `cloud_cover`·`visibility`
- `fetch(when)` / `fetch_series(start, end)`(밤 구간을 **한 번의 호출로**)
- **총운량 단일 축**. 층별 차폐율은 채택하지 않았다 (`decisions.md` §2.1)
- **완료 기준(회귀 픽스처)**: 경계값 10.0 / 30.0 / 50.0 이 각각 최적 / 양호 / 밝은 별 한정으로
  떨어질 것(`_EPS` 로 부동소수점 경계 보호). 결측은 '불가'가 아니라 **'알 수 없음'** ✅

> P7 에서 위성 실측이 들어오면서 이 축의 역할이 **예보 담당**으로 좁혀진다. 자세한 것은 P7.

### P4 — 밤 집계 ✅
- `core/tonight.py`: `night_window` 의 매 정시를 judge 로 판정해 집계
- `summarize()` → `observable_hours` · `by_grade` · `photometric_hours`/`spectroscopic_hours`
  (PTB/STB, 순수 운량 기준) · `windows` · `unknown_hours`
- **3시간 기준으로 가능/불가를 매기지 않는다** (`decisions.md` §2.6)
- `scope="night"` 파라미터로 진입 — 별도 도구를 만들지 않았다 (`decisions.md` §2.5)
- **완료 기준**: PTB ⊂ STB 불변식, 창 밖 정시 미포함, 0시간도 '불가'가 아닌 사실 서술 ✅

### P5 — 어둡기 축 (광공해) ✅
- `scripts/build_darkness_grid.py`(전처리, 연 1회) → `core/darkness.py`(런타임, numpy만)
- **nodata −999.9 마스킹 필수**. 격자 밖·해상은 `None` → "데이터 없음"
- 영점·자연광 상수를 **한 쌍으로 고정**(1.08e8 ↔ 0.171168465). 혼용 금지
- verdict 등급은 바꾸지 않고 **은하수 문구만** 정정 (judge 는 장소를 모르는 순수 함수로 유지)
- **완료 기준(회귀 픽스처)**: 용눈이오름 SQM 21.19 → Falchi iv / 제주시 SQM 19.18 → Falchi v ·
  Bortle 6 / 격자 분포 min 19.14 · p50 21.50 · max 21.93 ✅
- attribution 은 **Black Marble / LPM 귀속**을 축어로 (Falchi 인용이 아니다) ✅

> **남은 결함**: 은하수 문구가 SQM 만 보고 나간다. **보름달 밤에는 어디를 가도 은하수가
> 보이지 않으므로 이대로면 틀린 답을 낸다.** P8(달빛)에서 고친다.

### P6 — 어둡기 3신호 종합 + verdict 편입 ✅
- `core/nightlight.py`(VIIRS 근거리 광원) · `core/lamps.py`(가로등 9만 개) 신설
- `darkness.assess_site` 가 셋을 0~1 로 정규화해 가중합 → **등급 상한(cap)** 으로 judge 에 전달
- 가중합은 **어둡기 축 안에서만**. 구름·박명은 문헌 게이트로 유지 (`decisions.md` §2.12)
- 가로등 원본의 **위경도 뒤바뀜 15,514행을 교정**해서 쓴다 — 걸러내면 동부 중산간이
  통째로 '가로등 0개'가 된다 (`decisions.md` §1.8)
- **완료 기준(회귀 픽스처)** ✅

  - 상한 경계: 0.35 이하 제한 없음 · 0.60 이하 '양호' · 초과 '밝은 별 한정'
  - 게이트 불변식: 구름 90% + 최상급 어둡기 → **불가**(어둡기로 상쇄되지 않음)
  - 상한 불변식: 항해박명 + 최상급 어둡기 → '밝은 별 한정'(상한은 등급을 올리지 못함)
  - SQM 격자 밖이면 점수·상한 모두 `None`(보조 축만으로 판정하지 않음)

  삼는다. 창 크기 근거: 고도각 30° 컷오프 · 대표 운고 3km → 반경 5.2km
- **안개는 두 갈래로 쓴다**
  - **관측지 안개** → 관측 축. 지표 안개는 관측자를 감싸므로 하늘을 못 본다

  - 예보 시정을 판정에서 뺀 결정(`decisions.md` §1.3 · §2.3)과 충돌하지 않는다. 그 근거는
    *예보* 시정에 대한 것이고 위성 안개탐지는 실측이다 — 구분을 §1.3 에 적어 둔다
- **Open-Meteo 의 역할 재정의**: 판정의 주 입력이 아니라 **"이따 나빠진다" 경고** 담당.
  위성은 과거~현재만 있고 미래가 없다. `scope="night"` 집계는 계속 예보를 쓴다
- **'불가' 는 장소가 아니라 밤 전체에 붙는다** — *현재 흐림 AND 예보도 지속*일 때만
  "오늘 밤은 제주 전역이 어렵다" 헤드라인이 나간다. 그 경우에도 목록은 그대로 낸다
- **착수 조건**: `KMA_API_KEY`. `gk2a.py`·`core/cloud.py` 는 **작성 완료·커밋됨**, 엔진 미연결
- **완료 기준(회귀 픽스처)**
  - CLD 코드값 0·1 = 구름 / 2 = 청천 / 3 = TBD → 결측. 원본 −9999 포함 결측은 −1 로 통일
  - 창 경계: 비율 0.10 / 0.30 / 0.50 이 각각 최적 / 양호 / 밝은 별 한정
    (`decisions.md` §1.2 사다리와 같은 값)
  - 유효 화소 5개 미만이면 `None` — '불가'가 아니라 **'알 수 없음'**
  - 격자 역변환 검산: `xy_to_latlon(latlon_to_xy(p)) == p`
  - 제주 좌표가 한반도 격자 안으로 떨어질 것 (`index_of` 가 IndexError 를 내지 않음)

- K&S(1991) 달빛 산란을 **총 하늘밝기에 합산**한다. 식 (1)(2)(3)(15)(19)(20)(21)
- **식(2) 천정거리 보정 누락 금지** — 회귀 테스트로 강제한다. 소광계수 k=0.33 기본(조정 가능)
- 산란광 대기량 `X = (1 − 0.96·sin²z)^(−0.5)` 가 여기서 들어온다 (`decisions.md` §2.11)
- 출력에 **"무엇이 깎았나"**(달빛 / 광공해 기여분) 분해 표기
- **달은 후보 간 순위를 가르지 않는다.** 제주(약 80km) 안에서 달 고도차는 무시할 수 있어
  전역에 균일하게 작용한다. 영향을 주는 곳은 **밤 단위 헤드라인과 각 후보의 등급**이다
- **착수 단서 (인용 주의)**
  - K&S 식(2)(15)(19)의 절대상수는 1차 전문 미열람 상태다. 식(20)(21)·정확도 8~23%·
    k=0.172 는 교차확인됨 — 형태·검산이 정합하므로 구현은 진행한다
  - 보름달 근처(|α| < 7°) 정확도 저하는 K&S 원문 명시 한계 — **결과 문구에 반영**
- **완료 기준(회귀 픽스처)**: 별 수가 아니라 **하늘밝기(mag/arcsec²) 변화**로 고정한다
  - 달 없는 밤 대비 보름달·고도 45° 에서의 SQM 감소량
  - 그 결과 **은하수 문구가 '보임' → '소실' 로 뒤집히는 경계**
  - 달이 진 뒤(고도 < 0°)에는 기여가 정확히 0 일 것

### P9 — 후보 풀 200곳 (자동 발굴 + 데스크 검증)  ← 진행 중

**목표**: "숙소 근처"를 제주 어디서 물어도 답할 수 있게 한다.

`data/jeju_spots.json` 은 **120곳**이다 — 큐레이션 44 + 자동 발굴 76(장소
`kakao_sweep` 42 + 주차장 `kakao_parking` 34). 여전히 **엔진 미연결**이고, 아직 안 본
자동 발굴분은 `discovery` 키로 구분한다.

**발굴 직후 194곳이었다.** 검증이 묶음마다 빼면서 156곳(2026-08-10) → 131곳(08-11) →
120곳(08-12)이 됐다. 뺀 것의 대부분(49곳)이 주차장 발굴분의 **골프장·대학·병원·식당 사설 주차장**이다 — 해발 200m 이상만
보고 넣었으니 "야간에 남이 들어갈 수 있는 자리인가"가 걸러지지 않은 것이고, 그것을
사람이 보는 것이 이 단계다. 큐레이션분에는 더 좁은 지점으로 갈아탄 것이 섞여 있다
(산굼부리 → 산굼부리 주차장, 제주마방목지 → 관측지1·2). **빠지는 것이 정상 동작이므로
200곳은 발굴 목표이지 통과 목표가 아니다.**

**후보를 웹검색으로 모으면 30~40곳에서 포화한다.** 뒤로 갈수록 같은 이름(1100고지·
마방목지·새별오름)이 반복되고, 정작 가장 어두운 곳은 후기가 없어 검색에 걸리지 않는다.
그래서 검색은 **속성 채우기**(주차·도보·야간개방)에 쓰고, 발굴은 자동화한다.

- **자동 발굴**(`scripts/sweep_place_candidates.py`) — 카카오맵 로컬 API 로 **이름 있는
  야외 장소**를 전수 수집(20개 키워드 → 2,334건)한 뒤 걸러 낸다. 도로 격자에서 좌표만
  뽑는 것과 달리 이름·주소·지도 등록이 이미 돼 있어 그대로 안내할 수 있다
  - 어둡기 종합 점수(P6) ∩ 주차 500m ∩ 주행 가능 도로 300m
  - `track`(농로·임도)·`service`(사유 진입로)는 도로로 치지 않는다
  - 한 시설이 여러 점으로 등록돼 있어(휴양림 화장실 2·4·5·6) **400m 근접 묶음**으로
    합치고 장소 자체를 가리키는 이름을 대표로 삼는다. 부속 항목은 버리지 않고
    그 묶음의 **주차 좌표·화장실 근거**로 붙인다
  - 자르는 기준은 **대표점 자신의 점수**다. 묶음 최솟값으로 자르면 실제로 안내할 좌표가
    기준보다 밝은 채로 통과한다(신양섭지해수욕장: 묶음 0.377 · 대표점 0.514)
  - 편입은 `scripts/merge_swept_spots.py`. 같은 곳이면 버리지 않고 **사실을 합친다** —
    '족은노꼬메오름 주차장'은 노꼬메오름의 주차 좌표다
- **중산간 주차장 발굴**(`scripts/merge_upland_parking.py`) — 위 수집은 이름이 장소를
  가리키는 곳만 잡는다. '동광육거리주차장'·'메밀밭주차장' 처럼 **주차장 자체가
  목적지**인 자리는 걸리지 않는데, 관광객이 밤에 실제로 서 있는 자리는 그런 데다.
  그래서 축을 뒤집어 카카오맵 주차장 1,912곳을 놓고 **해발 200m 이상**(도가 쓰는
  중산간 경계)만 남긴다 — 240곳 → 이미 있는 곳 157 합침 · 새로 83곳
  - **어둡기로 자르지 않는다.** 이 목록은 추천 결과가 아니라 사람이 손으로 채울
    후보 풀이라, 애매한 곳도 남기고 실측 점수를 `notes` 에 적어 판단 재료로 준다
  - 좌표가 곧 주차 지점이라 `parking` 키를 따로 두지 않는다(같은 좌표를 두 번 적는
    것이라 알려 주는 것이 없다). 이미 있는 관측지에 붙을 때만 주차 좌표가 된다
  - 해발높이는 저장소에 DEM 이 없어 Open-Meteo 로 받아 `outputs/` 에 캐시한다
- **필터를 먼저 조인 뒤** 어둡기 순으로 자른다. 순서를 뒤집으면 백록담·사라오름 같은
  **한라산 심부**가 상위를 차지한다 — 최암부는 대개 사람이 못 가는 곳이라는 뜻이다
- **토지소유**: 디지털트윈국토 **제주 토지소유공간정보**. 사유지 배제. `data/land`
  (1,555,461행) 를 받아 뒀으나 **아직 필터에 넣지 않았다** — 남은 작업이다
- **검증은 로드뷰 데스크 전수.** 현장 방문은 하지 않는다
  - 로드뷰로 알 수 없는 것: 야간 실제 밝기 · 현재 주차 가능 여부 · 노면 상태 · 야생동물 ·

  - → **응답에 면책 문구가 필수다**: "주간 로드뷰 기준 확인, 현장 상황은 다를 수 있음"
- **좌표를 하나로 두지 않는다** — `(주차 좌표, 관측 좌표, 도보 소요시간, 도보 유형, 도보 노면)`
  - 유형(`walk_type`)은 `평지` / `등반` 을 가른다. 오름은 주차장에서 정상까지 20~40분이고
    조명 없는 흙길이며 일부는 자연휴식년제로 야간 출입이 막힌다. 도로변 관측지와 같은

  - 걷는 길의 힘든 정도는 **국립공원공단 탐방로 등급제**(2018-10-01)를 그대로 쓴다

    DEM 이 답한다 — `server/core/elevation.py` 가 FABDEM 격자를 **편집기가 저장할 때
    그 자리에서** 읽는다(배치 `fetch_route_profile.py` 는 지웠다). 자체 3값(정비·계단·

  - **주차 좌표는 여럿일 수 있다**(`parking` 은 목록). 오름 하나에 들머리가 갈리면 대는

  도보 유형 · 야간개방 · 주의사항 · 화장실이 채워질 것. 목표 200곳이되 실제 수는 발굴
  결과에 따라 조정한다
- **현재 채움 상태** (2026-08-10 · 156곳 기준): `parking` 59 · `cautions` 24 ·

### P10 — `find_spots` 최소판

**목표**: 추천이 실제로 나온다. **이 단계부터 시연 가능하다.**

- 랭킹 = **어둡기 종합 점수(P6) + 구름(P7) + 달빛(P8)**. 거리는 아직 직선거리
- **판정과 정렬을 분리한다** — `judge` 의 등급 산출은 손대지 않는다. 등급을 만드는 데는
  여전히 가중합을 쓰지 않고(`decisions.md` §2.12), **같은 등급 안에서 순서를 정할 때만**
  구름·거리·위험을 쓴다. 경위는 `decisions.md` §2.13
- 중심점이 없으면 제주 전역 top N 으로 폴백한다
- **불투명 커서** 페이지네이션 (stateless, 세션 저장 안 함)
- **완료 기준**: 중심좌표(선택) + 반경 → 랭킹된 목록 + 다음 커서. 아래 스키마를 그대로 실을 것

### P11 — 접근성 (주행시간 · 주차 · 길찾기)

**목표**: "왕복 1시간 이내"를 실제 거리로 답한다.

- **`origin` 이 주어진 모든 경우에 경로를 답한다** — 추천(`find_spots`)뿐 아니라 단일 장소
  판정(`evaluate_spot`)에도 붙는다. "가는 동안 무엇을 조심하나"는 질의 형태가 아니라
  초행·야간 운전이라는 사용자 전제(§0)에서 나오기 때문이다. `origin` 이 없으면 목적지 자체의
  관측 조건과 일반 주의사항만 답한다
- **정체를 따지지 않으므로 오프라인 라우팅으로 충분하다** — 정적 도로망 + 도로등급별 속도.
  실시간 교통 API 가 필요 없어 `egress 0` 방침을 깨지 않고, 야간에는 오히려 더 정확하다
- **라우팅 구현(로컬 OSRM / 순수 파이썬 도로 그래프)은 이 단계에서 결정한다.** 그 전까지는
  직선거리 × 보정계수로 둔다
- 카카오맵 **길찾기 딥링크**를 응답에 실어 관광객이 바로 내비를 띄우게 한다
- **완료 기준**
  - 랭킹 기준이 직선거리 → 주행시간으로 승격
  - `origin` 을 준 `evaluate_spot` 응답에도 `route`(주행시간 + 경로 주의사항)가 채워질 것
  - `origin` 이 없으면 `route` 가 `null` 이고 나머지 필드는 그대로 나갈 것
  - 딥링크가 실제 앱에서 열릴 것

### P12 — 안전

**목표**: "가는 길에 무엇을 조심해야 하나".

- **고정 위험**(장소의 성질): 급커브 · 가로등 없는 구간 · 절벽 · 야생동물 출현 ·
  야간 출입 제한 · 폭 좁은 중산간 도로(초보운전 주의). P9 검증 때 채운 필드를 쓴다

### P13 — 지도 HTML

**목표**: 좌표를 말로 설명하지 않는다.

- **정적 HTML 생성 → URL 반환.** 세션 상태를 만들지 않으므로 stateless 방침을 유지한다
- 베이스맵은 미리 생성해 두고, 요청마다 **핀 · 경로 · 주의구간만** 덧그린다
- Host LLM 에 URL 을 전달해 사용자가 대화창에서 연다
- **범위 전제**: 우선 로컬(시연·개발) 접근까지. 외부 공개 주소는 배포(P15) 문제로 미룬다
- **Gradio 는 판정 경로에 넣지 않는다** — 별도 프로세스에 세션 상태가 생겨 stateless 방침과
  어긋나고, 온프레미스에서 반환 URL 을 외부 기기로 열 수 없다. 필요하면 발표 시연용 UI 로
  분리한다
- **완료 기준**: 생성된 HTML 이 핀 · 경로 · 주의구간을 표시하고 `map_url` 로 열릴 것

### P14 — 경로 탐색 (`find_spots_on_route`)

**목표**: "숙소 가는 길에 별 보기 좋은 곳".

- 중심점 반경이 아니라 **경로 버퍼** 탐색. 출발·도착 좌표를 받는다
- P11 의 라우팅을 재사용한다
- **완료 기준**: 경로에서 크게 벗어나지 않는 후보만 나올 것(우회 시간 상한)

## 4. 이후 단계

### P15 — 배포 (`egress 0` 복원)
- Docker / docker-compose
- `batch-worker` 분리: Open-Meteo 를 배치로 받아 파일로 떨구고 MCP 서버는 **파일만 읽음**
- 현재는 서버 직접 호출 + `requests_cache`(1h). 경위는 `decisions.md` §2.10
- `map_url` 의 외부 접근 주소도 여기서 다룬다

### P16 — 천체 방향
- "어느 방향을 보면 어느 별이 있나". OpenNGC(pyongc) + de421 행성
- 별 **개수**는 내보내지 않는다(아래 폐기 항목). 밝은 대상의 **방위·고도**만 답한다
- 면밝기 `μ_V = V + 2.5·log10(π/4·a·b)`. **SurfBr 필드를 쓰지 말 것** (B밴드·은하 전용)

### P17 — 지형 개활도
- **FABDEM 격자(`core/elevation.py`)를 그대로 쓴다** — P9 에서 이미 깔렸다. 계획 당시
  적어 둔 Copernicus GLO-30 은 DSM 이라 수관·건물이 섞이는데(`decisions.md` §2.17),
  지평선을 재는 데는 오히려 **그게 맞을 수도 있다** — 사람의 시야를 실제로 가리는 것은
  맨땅이 아니라 서 있는 나무다. 어느 쪽인지는 이 단계에서 정한다
- 방위별 지평선 프로파일로 현재의 **하한 10° 일괄**을 정밀 차폐로 승격
- 오름 정상(사방 트임)과 도로변(한쪽 막힘)의 차이가 여기서 갈린다

### 폐기 — 별 개수 ("오늘 밤 별 약 N개")

관광객 프레이밍에서 **개수는 의사결정에 쓰이지 않는다.** "별 1,847개"는 어디로 갈지를
정하는 데 도움이 되지 않고, 그 자리에 실제로 필요한 것은 주차·화장실·가는 길 주의사항이었다.

- **함께 폐기**: Crumey(2014) 한계등급, BSC5 성표, 하늘 SQM 별 별 수 픽스처 표
- **살아남은 것**: K&S(1991) 달빛 산란 → **P8**. 개수를 안 내보내도 **달빛이 하늘밝기를
  깎는 것은 판정에 필요**하기 때문이다
- Crumey 인용 주의(자기 식 Eq.54 를 μ=22.0 에 대입한 6.22~6.24 와 인용문 6.18 의 불일치)는
  한계등급을 쓰지 않게 되면서 함께 유효성을 잃었다. 다시 도입한다면 이 노트부터 복원한다

### 폐기 — 방위 프로파일

VIIRS 를 16방위로 쪼개 "어느 쪽을 볼까"를 답하려던 단계다. **채택하지 않았다** —
관측지를 고르는 시점의 질문은 "여기가 어두운가"이지 "여기서 어느 쪽을 볼까"가 아니고,
실측에서 12지점 중 5지점(42%)이 거리감쇠 지수에 따라 추천 방위가 뒤집혔다. 경위와
K&S 대기량 식의 처리는 `decisions.md` §2.11.

VIIRS 는 방위를 쪼개지 않고 **근거리 광원 탐지**로 P6 에 들어갔다.

## 5. 도구 구성

§1 고정 1 대로 엔진은 하나고 진입점만 다르다. 질문 유형이 실제로 다른 것들만 도구를 가른다
(`decisions.md` §2.5).

| 도구 | 입력 | 답하는 질문 | 단계 |
|---|---|---|---|
| `find_spots` | `origin?` · `when?` · `max_drive_minutes?` | "오늘 밤 별 보기 좋은 곳" / "숙소 근처" — `origin` 없으면 제주 전역 top N | P10 |
| `find_spots_on_route` | `origin` · `destination` · `when?` | "숙소 가는 길에" | P14 |
| `evaluate_spot` | `place｜coords` · **`origin?`** · `scope` · `when?` | "지금 A 가면 잘 보일까" — 기존 두 도구를 합침 | 기존 |
| `tonight_outlook` | `date?` | "오늘 밤 어때" — 헤드라인 · 박명 시각 · 달 · 전역 구름 | P7·P8 |

**`origin` 은 두 도구에 공통으로 붙는다.** *출발지가 있나*와 *목적지를 지정했나*는 직교하는
축이라 네 경우가 각각 나온다:

| | **출발지 없음** | **출발지 있음** |
|---|---|---|
| **목적지 미지정** | 제주 전역 top N. 거리 축만 빠짐 | 주행시간으로 반경을 자르고 **거리를 순위에 반영** |
| **목적지 지정** | 그 장소 평가 + 일반 주의사항 | 그 장소 평가 + **출발지→목적지 경로 주의사항** |

즉 **출발지가 있으면 목적지를 지정했든 아니든 경로를 함께 답한다.** "가는 동안 무엇을
조심하나"는 추천에만 붙는 정보가 아니라 초행·야간 운전이라는 사용자 전제(§0)에서 나오는
것이라, `origin` 을 `find_spots` 에만 두면 "지금 성산일출봉 가면 어때?"에 가는 길을 못 답한다.

> `scope="moment"｜"night"` 는 **파라미터로 남긴다.** "밤이냐"와 "어떻게 입력하냐"는 직교하는
> 축이라, 밤을 별도 도구로 빼면 래핑이 복제된다 (`decisions.md` §2.5).

## 6. 왜 이 순서인가

1. **어둡기(P5)를 실시간 축보다 먼저** 끝낸 이유: 장소의 고정 속성이라 실시간 의존이 없고,
   한 픽셀 조회로 즉시 가치가 난다.
2. **지오코딩(P2)이 앞으로 온 이유**: 계획은 뒤(구 P8)에 뒀지만, 좌표를 직접 넣는 것보다
   지명을 넣는 게 실사용 진입 장벽을 훨씬 크게 낮춘다. 구현 비용도 작았다.
3. **어둡기를 한 축이 아니라 세 신호로 키운(P6) 이유**: 큐레이션 관측지 20곳 중 19곳이
   Falchi iv 라 SQM 하나로는 순위가 갈리지 않았다. 랭킹의 기준이 되려면 같은 등급 안을
   가르는 분해능이 먼저 필요했다.
4. **위성 구름(P7)·달빛(P8)이 후보 풀(P9)보다 먼저인 이유**: 둘 다 **지금 있는 엔진을 즉시
   더 정확하게** 만든다. 특히 달빛은 은하수 문구가 틀릴 수 있는 결함을 고친다. 후보를
   200곳으로 불려도 판정이 틀리면 추천 전체가 틀린다.
5. **후보 풀(P9)이 추천 도구(P10)보다 먼저인 이유**: 도구는 껍데기다. 20곳으로 추천을 만들면
   "숙소 근처에 후보 없음"이 자주 나오고, 그게 시연에서 제일 아픈 실패다.
6. **접근성·안전(P11·P12)이 추천(P10) 뒤인 이유**: 랭킹은 어둡기·구름만으로도 동작한다.
   먼저 동작하는 추천을 세우고, 거리·위험을 순위 기준으로 승격한다.
7. **별 개수를 버린 이유**: 개수는 어디로 갈지를 정하는 데 쓰이지 않는다. 그 자리에
   주차·화장실·주의사항이 들어갔다.
8. **방위 축을 버린 이유**: 사용자는 아직 그 자리에 있지 않다. "여기가 어두운가"가 먼저이고
   "어느 쪽을 볼까"는 도착한 뒤의 질문이다 (`decisions.md` §2.11).
